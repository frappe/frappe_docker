What the agent hands over, in the two forms a burger shop needs.

Assume the WhatsApp AI module exists. Two outputs, one order, two stages of the rollout

Output A — the order card. Plain text, laid out in the order the ERPNext form asks for it. Stage 1: the agent drafts, a human keys it in. Also the permanent fallback for when the API is unreachable, and the version to show the client, because it needs no explanation.

Output B — the REST payload. The same order as one POST. Stage 2: nobody types anything. The order appears in New on the kitchen board within a second of the customer saying yes.

Both describe the same order, SAL-ORD-2026-00007, which exists on the instance and has already been through the full pipeline to Delivered and invoiced.

Section 1 · Boundary

Where the agent stops and ERPNext starts

The AI module is middleware — a separate service holding the webhook, the session state and the model. It is not code inside ERPNext. Everything it does to the ERP it does over the REST API as an ordinary authenticated user. That boundary is what lets you swap the model, or turn the agent off entirely, without touching the ERP.

What the middleware owns

  1. Receive the WhatsApp webhook
  2. Identify the customer by phone — find or create
  3. Hold the conversation state across turns
  4. Log every message as a WhatsApp Message linked to the customer
  5. Create and advance the Sales Order over REST
  6. Send the outbound template on each status change
  7. Escalate into a human’s queue when the guardrails say so

What ERPNext owns

The menu and its prices. The customer master. The order and its state machine. The money. Every rule that must not be negotiable — because a rule enforced in the middleware is a rule an LLM can be talked out of, and a rule enforced in the workflow is not.

The middleware authenticates as its own ERPNext user holding Burger Order Desk and Sales User. Generate an API key and secret on that user; never ship the Administrator’s.

Section 6 · Moves

Advancing the order

Once the order exists, every further change of state goes through the workflow. The middleware does not write custom_order_status as a free field — it asks for a transition and lets the server decide.

workflow transitions
# 4. Move an order along. This is the ONLY correct way — it runs the
#    workflow: role check, condition check, and the docstatus change.
POST /api/method/frappe.model.workflow.apply_workflow
{
  "doc":    { ... the full Sales Order document, as fetched ... },
  "action": "Confirm"
}

# Fetch it first:
GET /api/resource/Sales%20Order/SAL-ORD-2026-00007

# Post-submit moves can also be done as a plain field write — this is
# exactly what the Kanban board does, and the workflow still validates it:
POST /api/method/frappe.client.set_value
{
  "doctype":   "Sales Order",
  "name":      "SAL-ORD-2026-00007",
  "fieldname": "custom_order_status",
  "value":     "Ready"
}
# -> 417 WorkflowPermissionError if that move is not legal for this user.
#    Do NOT use set_value for New -> Confirmed: that transition also has to
#    submit the document, and set_value cannot. Use apply_workflow.
Watch outConfirmed → In Kitchen carries the condition advance_paid >= grand_total. Until a Payment Entry is recorded the action does not exist — the API returns Not a valid Workflow Action. The agent should treat that as the expected answer for an unpaid order, not as a failure to retry.
Section 7 · Escalation

Handing it back to a human

The escalation path has to land somewhere a person will actually look. Assignment plus a comment does that: the order appears in the desk’s notifications, and the reason survives on the document.

escalate
# 5. Hand off to a human. Two failed clarifications, any complaint,
#    any refund, any order over the value cap.
POST /api/method/frappe.desk.form.assign_to.add
{
  "doctype":     "Sales Order",
  "name":        "SAL-ORD-2026-00007",
  "assign_to":   ["desk@habibi-burger.example"],
  "description": "Customer disputes the delivery fee. Asked twice, not resolved.",
  "priority":    "High"
}

# If there is no order yet, assign the Customer instead.
# Always also leave the reason as a comment so it survives reassignment:
POST /api/method/frappe.desk.form.utils.add_comment
{
  "reference_doctype": "Sales Order",
  "reference_name":    "SAL-ORD-2026-00007",
  "content":           "AI agent escalated: fee dispute, 2 failed clarifications.",
  "comment_email":     "agent@habibi-burger.example",
  "comment_by":        "Habibi WhatsApp agent"
}

Section 9 · Guardrails

The rules, as the middleware must implement them

From the scope document, restated as things a developer can test. The ones that can live in ERPNext already do — the rest are the middleware’s responsibility.

RuleHow it is enforced
Never invent an item or a priceEvery line must resolve to an item_code from the Habibi Menu price list. If it is not on that list, the agent says so and offers the nearest real thing.
Always read back before writingThe full order, the total and the address, then an explicit yes. The read-back is what makes a wrong order the customer’s correction rather than the kitchen’s waste.
Two strikes, then a humanAfter two failed clarification attempts on the same slot, escalate. Do not loop.
Complaints and refunds are never the agent’sRoute immediately, without attempting resolution.
Cap the order valueAbove an agreed ceiling, a human confirms before the order is written. The cap is still to be set — open question for the workshop.
Never go silentIf ERPNext or the model is unreachable, say a human will reply. Silence is the one failure the customer always notices.
Section 10 · Failures

What the API says when it says no

Every one of these is a real response from this build. The agent needs a branch for each; a generic retry loop will make three of them worse.

ResponseWhat it means and what to do
417 · Not a valid Workflow ActionThe move is blocked by a condition — almost always the payment gate on Confirmed → In Kitchen. Not an error: it is the rule working. Do not retry; tell the customer the order starts once payment clears.
417 · Workflow State transition not allowedThe move is illegal from the current state, or the user lacks the role. Re-read the order’s current status before deciding what to do — a human may have moved it under you.
409 · Document has been modifiedSomeone edited the order between your fetch and your write. Re-fetch and re-apply. Never blind-retry the stale document.
403API key lacks the role. Check the middleware user has Burger Order Desk plus Sales User.
VAT comes back as 0You sent taxes_and_charges without the taxes rows. The template does not expand server-side over REST. Post the rows explicitly — this is the single most common integration mistake on this build.
ERPNext unreachableDo not go silent. Reply to the customer that a human will follow up, queue the order locally, and raise an alert. This is a non-negotiable guardrail from the scope document.
